# Profile & Social graph — polish pass

[← Back to the punch list](../punch-list.md)

Scope: `(buyer)/profile.tsx`, `(tabs)/profile.tsx`, `seller-profile.tsx`, `buyer-other-profile.tsx`, `(buyer)/edit-profile.tsx`, `edit-profile.tsx`, `share-profile.tsx`, `share-store.tsx`, `connections.tsx`, `(buyer)/following.tsx` / `(tabs)/following.tsx`, `profile-products.tsx`, `profile-videos.tsx`.

## Starting point

This cluster was already carrying real prior investment (`#72`/`#80`/`#82`): every profile screen renders into a shared `ProfileShell` (`components/profile/ProfileShell.tsx`) — a full-bleed collapsing cover-video hero, avatar with story ring, display-size name, tabular stats row, a 2×2 action-button grid, an animated tab strip, and a virtualized grid, all themed off `useAppTheme()` with no static color imports. `ProfileControls.tsx` supplies 44pt interactive primitives (`ProfileButton`, `ProfileGlassButton`, `ProfileStatsRow`, `ProfileTabs`, `ShopPill`) with hover/press/focus states baked in. Most of the P0s called out in `docs/polish/screens/03-buyer-social.md` for this slice (grid tiles rendering real media, QR white-on-white, fallback-avatar contrast, follow being fire-and-forget, sign-out/delete confirmations, "Jordan" placeholder identity, etc.) were already fixed in the current code — verified by reading each file, not assumed.

Given that base, this pass is a verification + targeted-polish pass: boot every screen for real, compare against Mobbin references, and fix what was still measurably weak, rather than re-deriving a design that was already sound.

## Known limitations of this pass

- This dev container has no live API backend, so every screen above ran against the real network stack but with no data to return. Grids, stats, and load states you see in the "after" shots are the genuine loading/empty states (skeletons, "–" placeholders), not a stand-in — but content-bearing states (an actual filled-in profile, a populated followers list) couldn't be screenshotted here. Code for those states was reviewed directly (not just inferred from behavior).
- `seller-profile.tsx` / `buyer-other-profile.tsx` were screenshotted by deep-linking directly to their URL, which mounts them without the stack-over-tabs context they're normally pushed into from in-app navigation; a tab-bar row visible at the very bottom of those "after" shots is an artifact of that direct-URL harness, not a change introduced here.
- The long-standing `(buyer)` vs `(tabs)` route-name collision on `/profile` and `/following` (both groups register a file at the same URL) is a pre-existing, cross-cutting routing issue called out in `docs/polish/punch-list.md` as unresolved. Fixing it means renaming routes and touching navigation call sites across every other cluster (Settings, Thread Cash/Notifications, Onboarding, Threads feed/Messages), so it was deliberately left alone in this single-area pass — noted here rather than silently worked around.

## Shared-component changes (visible to other sessions)

- `app/seller-profile.tsx` and `app/buyer-other-profile.tsx` (both in this cluster) now import `useBuyerTabBarInset` from `components/buyer-nav/buyerTabBarMetrics` — a read-only hook call; no shared file was edited.
- No files under `components/`, `contexts/`, or `lib/` were modified. `connections.tsx` defines its own local `FollowPill` (not exported) instead of reusing `components/ui/MotionPrimitives`'s `FollowMorphButton`, specifically to avoid pulling `react-native-reanimated` into that screen's import graph, which was breaking `tests/connections-navigation.test.tsx`'s hand-rolled `react-native` mock. This is scoped to `connections.tsx` only and changes no shared file.
