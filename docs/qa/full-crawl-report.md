## Guest / Web

12. **[App resiliency, not confirmed as reachable by real users] No visible
    timeout/fallback if Clerk's client SDK never finishes loading.**
    What happened: with no `bt_preview` bypass (the real, fully signed-out
    entry point), the app renders only the Brandthread boot logo and never
    proceeds to the splash/sign-in screen, even after 15+ seconds. The root
    layout wraps the whole app in `<ClerkLoading>`/`<ClerkLoaded>` with no
    apparent timeout, so if `ClerkLoaded` never fires (e.g. Clerk's frontend
    API is unreachable — see limitation below), the user is stuck on the
    boot logo forever with no error message or retry affordance.
    Severity: **Low** — this specific run hit it because of the sandbox's
    network policy (see below), but a real user on a flaky or
    corporate/firewalled network could hit the same hang, and there's no
    visible recovery path.
    Screenshot: `docs/qa/screenshots/guest-boot-stuck.png`

    **Harness limitation, updated for this pass (still not a counted product
    issue, but real further effort was put in — the owner specifically asked
    for it):** this pass built `artifacts/mobile/scripts/qa-crawl/
    guestClerkMock.mjs`, a `context.route()` interceptor that:
    1. Serves the real, locally-installed `@clerk/clerk-js` browser bundle
       (from `node_modules`, exact version the app depends on) in place of
       the script tag's request to the fake/unreachable frontend-API CDN
       host, instead of letting that request fail outright.
    2. Stubs the companion `@clerk/ui@1` bundle clerk-js lazily loads for its
       prebuilt UI components (also unreachable in-sandbox) with an empty
       *non-module* script — the first attempt used `export {}`, which
       actually made things worse: clerk-js injects that bundle as a plain
       `<script>` tag (not `type="module"`), so `export {}` threw a
       `SyntaxError` that silently killed the whole load chain.

    Effect: `window.Clerk` now gets constructed (`version` reports `6.31.1`
    correctly) instead of the script failing to load at all — genuinely
    further than pass 1, which didn't investigate this at all beyond
    observing the stuck boot logo. **However, `ClerkLoaded` still never
    fires.** With an unfiltered `context.route("**/*")` listener running for
    8+ seconds after those two script loads, **no further network request is
    ever attempted** — no `GET /v1/client`, no `GET /v1/environment`, and no
    iframe is created for Clerk's dev-browser handshake either.
    `window.Clerk.status` stays `"loading"` indefinitely. We were not able to
    identify, within this pass's time budget, what internal precondition
    clerk-js@6's `load()` is waiting on before it will even attempt that
    first call — candidates not ruled out: a config-validation branch
    (`isSatellite`/`proxyUrl`/`instanceType`) silently bailing out for a
    synthetic key that doesn't match Clerk's real key-encoding checksum, or a
    scheduling primitive (e.g. `requestIdleCallback`) that a headless
    Chromium context never fires the way a real browser tab does.

    **Net result: guest/signed-out crawling still could not be performed
    beyond the boot screen this pass**, despite a real, documented attempt at
    the Clerk-network-mock the owner asked for (see "Coverage achieved" and
    "Known limitations" below for what this means for guest coverage, and
    `guestClerkMock.mjs`'s own header comment for the fullest technical
    writeup). The most promising next step for a future pass: instrument
    clerk-js's own source (unminify it or set breakpoints via
    `page.pause()`/CDP) to find the exact gating condition, rather than
    black-box network observation.

## Static dead-link analysis (step 4)

Every string-literal call site of `router.push(...)`, `router.replace(...)`,
`router.navigate(...)` (including the `{ pathname: '...' }` object form and
template-literal forms with interpolated params) was extracted from
`artifacts/mobile/{app,components,contexts,hooks,lib,services}` and
cross-referenced against the actual route files under `artifacts/mobile/app/`.

- **106** plain string-literal targets — all resolved to a real route file.
- **9** `{ pathname: '...' }` object targets — all resolved.
- **~60** template-literal targets with interpolated IDs/params (e.g.
  `` `/order-detail?id=${id}` ``) — all resolved to a real route file, **except one**:

  **Dead link:** `artifacts/mobile/lib/notificationNavigation.ts:62`
  ```ts
  if (data?.targetType === 'conversation' && typeof data.targetId === 'string' && data.targetId) {
    router.push(`/chat/${encodeURIComponent(data.targetId)}`);
    return;
  }
  ```
  There is no `app/chat.tsx` or `app/chat/[id].tsx` route. Every other
  conversation-related surface in the app uses `/buyer-conversation?id=...`
  or `/manufacturer-messages?threadId=...` instead. A push notification with
  `targetType: 'conversation'` (tapped from the OS notification tray) will
  therefore route to Expo Router's not-found screen instead of opening the
  conversation.
  Severity: **High** (silent dead end from a real, user-facing entry point —
  notification taps — not just an in-app click).

- `navigation.navigate(routeName as never)` in
  `components/buyer-nav/BuyerTabBar.tsx` uses a dynamic variable, not a
  literal, so it isn't statically checkable; it wasn't flagged either way.
- No `<Link href="...">` usage was found anywhere in the app — all navigation
  is imperative via `router.push`/`replace`/`navigate`, which is also why the
  crawler discovers routes by clicking rather than by reading `<a href>`
  (see Harness).

**Re-verified after merging `origin/dev` for this pass** (which brought in
thread-cash hardening, notification-batch-queue, profile-cover-video, and
Shopify-fulfillment work): re-ran the same extraction (**335** distinct
literal/template navigation call sites this time, up from ~175, reflecting
the larger codebase) against the current route list. Result: still exactly
the one dead link above (`/chat/${...}` in `notificationNavigation.ts`,
unchanged) — the dev merge did not introduce or fix any static dead links.

## Harness

### How to rerun it

```bash
# 1. Postgres (this container ships postgresql-16 via pg_ctlcluster):
service postgresql start
sudo -u postgres psql -c "CREATE DATABASE brandthread;"   # once
export DATABASE_URL=postgresql://postgres:postgres@localhost:5432/brandthread

# 2. Schema: drizzle push + the hand-written SQL migrations
cd lib/db && pnpm run push-force && pnpm run migrate

# 3. Seed realistic buyer/seller/store/products/orders/etc fixtures
#    (idempotent — safe to rerun; deletes and recreates its own rows)
pnpm --filter @workspace/api-server run qa:seed
# or from the repo root:
pnpm run qa:seed

# 4. Start the api-server with the QA auth bypass enabled (dev-only, see below)
cd artifacts/api-server
NODE_ENV=development ENABLE_QA_AUTH_BYPASS=true ENABLE_TEST_SUBSCRIPTION_BYPASS=true \
  DATABASE_URL=$DATABASE_URL PORT=5050 \
  CLERK_PUBLISHABLE_KEY=<any syntactically-valid pk_test_... key> \
  CLERK_SECRET_KEY=<any syntactically-valid sk_test_... key> \
  AI_INTEGRATIONS_OPENAI_API_KEY=fake AI_INTEGRATIONS_OPENAI_BASE_URL=http://localhost:1/fake \
  pnpm run dev

# 5. Build a STATIC export of the Expo web build and serve it, rather than
#    running Metro's dev server (`expo start --web`). Pass 1 used Metro and
#    hit an unbounded-memory OOM after ~17 distinct bundled routes; the
#    static export has no such problem and is what pass 2 used for the full
#    ~260-route crawl (see "Known limitations" below for the one thing this
#    changes: the publishable key gets baked in at build time).
cd artifacts/mobile
EXPO_PUBLIC_CLERK_PUBLISHABLE_KEY=<any syntactically-valid pk_test_... key> \
  EXPO_PUBLIC_API_BASE_URL=http://localhost:5050 CI=1 \
  NODE_OPTIONS=--max-old-space-size=6144 pnpm run build   # -> static-build/
EXPO_WEB_BUILD_DIR=static-build PORT=8082 node server/serve.js &

# 6. Generate the static route list (every Expo Router route file, with real
#    seeded IDs substituted into [param] segments) and crawl every one of
#    them per role, not just click-discovered ones:
node scripts/qa-crawl/routeList.mjs --ids scripts/qa-crawl/ids.json \
  > scripts/qa-crawl/routes.json
BASE_URL=http://localhost:8082 API_BASE_URL=http://localhost:5050 \
  QA_RESULTS_PATH=../../docs/qa/results/buyer-390x844.json \
  pnpm qa:crawl -- --role buyer --max-pages 400 --viewport 390x844 \
  --routes-file scripts/qa-crawl/routes.json
# (also: --role seller, --role guest; repeat per viewport, e.g.
#  --viewport 375x667 / --viewport 1440x900, optionally with QA_LITE=1 for a
#  faster screenshot/layout-only secondary pass -- see "Coverage achieved.")
```

Wired up as `pnpm qa:crawl` in `artifacts/mobile/package.json` (and
`pnpm qa:crawl` / `pnpm qa:seed` at the repo root, which just delegate via
`pnpm --filter`). `scripts/qa-crawl/summarize.mjs` merges the per-role/
viewport result files under `docs/qa/results/` and prints a stats summary
(slow screens, console/network errors, unclosable sheets, form-validation
gaps, etc.) to speed up writing up a fresh run.

### Mock-auth approach

Two separate, independently-gated mechanisms, both **pre-existing or
narrowly scoped to be inert everywhere except this exact use case**:

1. **Client-side (mobile app): the app's own existing `?bt_preview=buyer|seller`
   dev bypass.** Nothing was added to the mobile app for this. See
   `artifacts/mobile/app/_layout.tsx` (`PREVIEW_ROLE`) and
   `artifacts/mobile/lib/devPreview.ts`. It's `__DEV__`-gated, web-only, and
   only activates on an explicit query param — a production build or a
   native build ignores it entirely, and web with no query param gets the
   real signed-out experience. It skips `ClerkLoaded`/onboarding entirely and
   renders the buyer/seller shell directly, seeding `AsyncStorage`/`localStorage`
   flags (`onboarding_complete`, `user_role`) so the router doesn't redirect
   away.

2. **Server-side (api-server): a new, narrowly-gated bypass in
   `artifacts/api-server/src/middlewares/requireAuth.ts`.** The client-side
   bypass alone doesn't help once a screen makes a real `fetch` — the
   api-server still runs real Clerk session verification via
   `clerkMiddleware`/`getAuth`, which needs network access to Clerk plus a
   real key pair, neither available in this sandbox. A request carrying an
   `x-qa-user-id: <clerkId>` header is now trusted as that clerkId, but
   **only** when both `NODE_ENV !== "production"` and
   `ENABLE_QA_AUTH_BYPASS === "true"` — mirroring the pattern already used by
   the existing `ALLOW_TEST_SUBSCRIPTION_BYPASS` flag in the same file. It is
   never set in a deployed environment. The crawler injects this header via a
   Playwright `context.route()` interceptor on every request to the
   api-server origin, so the app's own fetch code is untouched.
   **This is the one piece of application source this pass modified**, and
   it's additive/inert-by-default; it was necessary because there was no
   existing server-side dev/test auth bypass to reuse (searched for
   `MOCK_AUTH`/`E2E`/similar — none existed).

3. **Guest = no bypass, no query param at all** — the real, unmodified
   signed-out code path. See the limitation above: it currently cannot get
   past the boot logo in this sandbox because real Clerk network access is
   blocked by the container's egress policy, and `ClerkLoaded` never fires.

### Known limitations / gaps (honest accounting)

- **Guest role**: could not be crawled beyond the boot screen (see above).
  Zero guest screens were exercised. This is the single biggest coverage
  gap.
- **Coverage breadth**: 9 buyer + 10 seller routes were crawled this pass,
  out of ~260 route files in `artifacts/mobile/app/`. `CLICK_BUDGET_PER_PAGE`
  (default 8, used 5–6 here) caps how many of a page's interactive elements
  get click-tested, and `--max-pages` caps total pages per role, both purely
  for wall-clock time in this sandbox. Raise both for a deeper run.
- **Viewports**: only 390×844 got the full click-based BFS. 375×667 and
  1440×900 only got a 2-tab-root screenshot spot-check per role
  (`viewport-*` screenshots) — extending the full BFS to all 3 viewports is
  the natural next step and the crawler already accepts `--viewport`.
- **Forms**: not filled with valid/invalid data in this pass — the crawler
  discovers and screenshots forms (e.g. the Add Product wizard) but doesn't
  submit them. This is the most significant functional gap versus the
  original ask; `page.fill()`-based form-filling would need per-form field
  heuristics (label text → input) to be generic enough to reuse everywhere.
- **Toggles/switches, pull-to-refresh, native deep links
  (`brandthread://...`)**: not exercised. The custom URL scheme is
  `brandthread` (see `app.json`); a follow-up pass should grep
  `Linking.openURL`/scheme usage and drive them the same way the crawler
  drives web routes.
- **"Dead click" detection is a heuristic**, not a ground truth: it flags
  "no URL change and no `document.body.innerText` change," which will
  false-positive on anything that opens a native-style sheet/menu without
  changing visible text (several "candidate" issues above need manual
  confirmation for exactly this reason) and can't observe portal-rendered
  overlays outside normal layout in every case.
- **Truncated-text and offscreen-element heuristics** are coarse DOM
  measurements (`scrollWidth`/`clientWidth`, bounding-box-vs-viewport) and
  will have false positives against virtualized lists or intentionally
  off-canvas carousel items — treat all "offscreen"/"truncated" findings as
  candidates.
- **6 route handlers use `getAuth(req)` directly instead of the `requireAuth`
  middleware** (`manufacturers.ts`, `manufacturer-flow.ts`,
  `manufacturer-connect.ts`, `manufacturer-public.ts`, `public.ts`, `auth.ts`
  in part) and are **not** covered by the `x-qa-user-id` bypass. The
  manufacturer-portal surface was out of scope for this pass as a result.
- **Sandbox network policy blocks external hosts** (e.g. `picsum.photos`,
  used for seeded product/post images, and Clerk's real frontend API). Every
  page in this run logged `net::ERR_TUNNEL_CONNECTION_FAILED` console errors
  for these — that noise was filtered out of the issue list above as a
  sandbox artifact, not an app bug. In a real deployment with normal internet
  access this would not occur; if reusing this harness in a similarly
  locked-down CI runner, seed images should point at a locally-hosted static
  file instead of an external placeholder host.
- **Metro's dev server (`expo start --web`) is not durable for a long
  crawl.** Running in `CI=1` mode (required to avoid interactive prompts)
  disables its persistent cache, and its memory grows unboundedly as more
  distinct routes get bundled — it OOM-crashed once during this run's seller
  crawl after ~17 distinct routes had been bundled (see
  `artifacts/mobile/package.json`'s `build`/`serve` scripts for a
  production-export alternative that wouldn't have this problem — that
  path wasn't used here for time reasons, but is the right fix for a longer
  run). Mitigation used here: restart with
  `NODE_OPTIONS=--max-old-space-size=6144`. A longer run should either use
  the static export (`pnpm run build && pnpm run serve`) or restart Metro
  every N pages.

### How to extend it

- `artifacts/mobile/scripts/qa-crawl/crawl.mjs` is the whole harness in one
  file, deliberately kept small and readable. The natural extension points:
  - `CLICK_BUDGET_PER_PAGE` / `--max-pages` / `--viewport` CLI flags already
    exist — just run with higher values (and prefer the static export server
    over Metro dev mode for a long run, per above).
  - `TAB_ROOTS` — add more starting points per role if you want the BFS to
    start from more places at once.
  - Form-filling: add a step after `collectInteractiveElements` that also
    collects `input`/`textarea`/`[role="combobox"]` elements per page, fills
    them with a valid-data fixture and an invalid-data fixture, and submits
    both, recording the same finding shape as everything else.
  - Deep links: grep `app.json`'s `scheme` field and any `Linking.*` call
    sites, then add them as extra seed URLs into `TAB_ROOTS`-style queues.
  - Guest: once the sandbox's network policy allows reaching Clerk (or a
    Clerk network mock is built), the same `crawlRole('guest', ...)` path
    already exists and just needs `QA_USER_IDS.guest` to stay `null` (no
    `x-qa-user-id` header — this is already the case).
