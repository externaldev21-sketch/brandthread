# 1:1 audio + video calls in DMs — Instagram flow mapping

**Spec, not inspiration.** Per the owner's instruction, the Mobbin flow below is matched 1:1 — screen order, layout, spacing, hierarchy and copy (adapted to our names) — with only the skin swapped to Brandthread's monochrome system (no Instagram blue, no Instagram icon set/fonts/corner shapes). The one allowed accent color anywhere in this feature is the red end-call/decline button.

**Reference flow:** [Instagram iOS — "Calling a user"](https://mobbin.com/flows/a8a5ca12-7000-4bd2-9595-ad4abdae9308) (5 screens). Related flows walked for context: [Messaging a user](https://mobbin.com/flows/734039f9-2f24-4f6f-8297-20dc427607cf) (header call buttons in the resting chat state) and [Watching together](https://mobbin.com/flows/fb105c10-250d-4873-ac13-2ba8d0993885) (shares the same in-call chrome as a video call, confirming the control-bar treatment is one shared component in Instagram's own app, not a one-off per feature — same principle we're applying here).

## Provider decision: reuse Agora — no new signup needed for PR1

The app already has a working Agora integration for the LIVE feature (`lib/live/*`, `AGORA_APP_ID`/`AGORA_APP_CERTIFICATE`), and — discovered mid-investigation — **a real, working 1:1 Agora call screen already exists** at `app/call-screen.tsx`, wired from both `app/buyer-conversation.tsx` and `app/seller-conversation.tsx` header call buttons, plus `app/manufacturer-messages.tsx`. It:

- Fetches a scoped Agora RTC token from `POST /api/call/token` (`artifacts/api-server/src/routes/call.ts`), which already authorizes both ordinary DM participants (via `conversationParticipants`) and manufacturer-thread participants.
- Joins an Agora channel in `ChannelProfileCommunication` mode (Agora's dedicated 1:1/small-group calling profile — distinct from the `ChannelProfileLiveBroadcasting` mode the LIVE feature uses), with mute/camera-toggle/screen-share/hang-up controls.
- Has token renewal and call-lifecycle event auditing (`started`/`ended`/`declined`/`failed`) — but **only for manufacturer threads** (`getManufacturerCallThread` in `call.ts` restricts `/api/call/token/renew` and `/api/call/events` to the `manufacturer_threads` table). Ordinary buyer/seller DM calls get an initial token only, no renewal, and no server-side lifecycle logging/notification.

**Decision: keep Agora.** `react-native-agora` is already a mobile dependency; the server-side token/channel logic is already correct for regular DMs. No new vendor, no new signup, no new native module to add.

**What's actually missing is not the provider — it's the product surface around it:** a matching outgoing/incoming/in-call/ended UI (Instagram-exact, not the current bare-bones layout), minimize-to-bar (the current screen hangs up on unmount), incoming-call signaling (no websocket/push layer exists yet — `lib/live/apiLiveProvider.ts` notes the same gap and polls instead), and call-log bubbles in the thread (no such message type exists client- or server-side today). That surface is this PR pair.

**What PR2 needs from the owner** (nothing is needed for PR1 — see the split below):
- Real `AGORA_APP_ID` / `AGORA_APP_CERTIFICATE` values from [console.agora.io](https://console.agora.io) (free tier: 10,000 free minutes/month) — `.env.example` currently only has placeholders (`replace_me`). Without these, `/api/call/token` returns `503 CALLING_NOT_CONFIGURED` and the app must show "Calls aren't available right now" (already implemented in `app/call-screen.tsx`).
- A decision on the incoming-call signaling transport for ordinary DMs: reuse the existing notification pipeline (`publishNotification`, already used for manufacturer call events) plus client-side polling (matching `lib/live/apiLiveProvider.ts`'s `POLL_MS = 3000` pattern), or invest in a real push/websocket layer. Either is viable; polling is the lower-risk PR2 default given the codebase has no realtime layer anywhere yet.
- CallKit (iOS) / ConnectionService (Android) for a true lock-screen incoming-call UI needs a custom dev build — Expo Go and a bare managed build cannot register a CallKit provider. Documented as a gap below, not attempted in either PR.

## Architecture (PR1)

- `lib/calls/types.ts` — `CallSession`, `CallStatus` (`outgoing` / `incoming` / `connected` / `ended`), `CallMode`, `CallPeer`, `CallLogEntry`, and the `CallProvider` interface every implementation (preview, and Agora in PR2) implements identically — same "one interface, swappable provider" shape as `lib/live/types.ts`.
- `lib/calls/previewCallProvider.ts` — the **only** provider wired in PR1: a fully simulated call (auto-rings, auto-connects, simulates the peer's camera going off) with zero network/media. This is what "preview-mode simulated call" in the PR split means — the whole flow is screenshotted and demoable without Agora credentials.
- `lib/calls/CallSessionContext.tsx` — one app-wide call session (never more than one call at a time), alive across navigation. Deliberately **not a route**: Instagram's call UI floats above the whole app and survives navigating around while minimized, which a pushed screen can't do (unmounting would hang up the call). Rendered by `components/calls/GlobalCallOverlay.tsx`, mounted once at the app root, as an absolute-fill layer above the navigator.
- `components/calls/*` — the five screens above, all monochrome, built on the shared `PressableScale`/`IconButton`/typography/spacing tokens from Phase 1/2's design system, never touching the existing (untouched, still-real) `app/call-screen.tsx`.

## PR split

- **PR1 (this one):** the full Instagram-mirror UI above, call-log bubbles, and the simulated preview provider. No changes to `app/call-screen.tsx`'s real Agora logic, and no changes to the manufacturer calling flow — both keep working exactly as they do today.
- **PR2:** `lib/calls/agoraCallProvider.ts` implementing the same `CallProvider` interface by adapting the engine logic already proven in `app/call-screen.tsx` (token fetch, `createAgoraRtcEngine`, join/leave, mute/camera/renewal), incoming-call signaling for ordinary DMs (poll-based, matching the LIVE feature's own pattern, or push if the owner wants to invest in a realtime layer), server-side call-log persistence (a new message kind or a lightweight `call_log` table + `GET` endpoint the two conversation screens can hydrate from on load), and a `/api/call/rating` endpoint to store the Good/Not good tap. CallKit/ConnectionService evaluated only if the owner confirms a dev build is in scope.

## Verifying the preview build

Web dev preview, matching the LIVE feature's existing convention:
- `?bt_preview=buyer` / `?bt_preview=seller` — the two conversation screens' call buttons open a fully simulated call end to end (outgoing → auto-connects → controls work locally → end → rating).
- `?bt_call=incoming` / `?bt_call=incoming_video` (added on top of `bt_preview`) — rings an incoming call on screen mount, for screenshotting the incoming-call screen without a second device.

Checked at 375×667 (iPhone SE), 390×844 (iPhone 15 Pro), and 430×932 (iPhone 15 Pro Max) via `artifacts/mobile/e2e/call-flow-screens.spec.ts` (Playwright, run manually against `pnpm exec expo start --web --port 8081` — same convention as the existing `e2e/*.spec.ts` files in this repo). Screenshots for each step (outgoing, in-call video with camera off, ended + rating, call log bubbles, outgoing audio) are in `artifacts/mobile/docs/polish/screenshots/call-flow/`, each paired with its Mobbin reference image at 390×844 in the PR description.

**Seller preview gap (pre-existing, not introduced by this PR):** `app/seller-conversation.tsx`'s `?bt_preview=seller` mode has no seeded preview thread/messages the way `app/buyer-conversation.tsx` does (`lib/previewInbox.ts`), so it fails to load a conversation in this sandboxed environment and couldn't be screenshotted end to end. This is unrelated to the call feature — every call UI component under `components/calls/` is a single shared implementation used identically by both `buyer-conversation.tsx` and `seller-conversation.tsx` (same `CallSessionProvider`/`GlobalCallOverlay`, same screens), so the buyer screenshots are representative of both surfaces. Seeding `seller-conversation.tsx`'s preview mode would be a good follow-up for whichever session owns that screen's polish.
