## Fixes
- `artifacts/mobile/lib/notificationNavigation.ts:221-227` — The "Ship now" action on a new-order push, and a `/subscription` push, called `router.push` directly and skipped the multi-account switch that a plain tap gets (`data.accountId`, the push's account, vs the active account). Failure: seller B's new-order push arrives while seller A is active, B taps "Ship now", and `/fulfill-order?orderId=` opens under A, so the order fails to load or shows the wrong account. The same happens with a trial-ending push for B, which opens A's Subscription. Fix: the switch logic now lives in an exported `openNotificationHref(router, href, data)` (:176), and the plain tap, Ship now and the subscription route all go through it. Test: `artifacts/mobile/lib/__tests__/notificationAccountSwitch.audit.test.ts` (failed before: yes, 2 of these cases)
- `artifacts/mobile/lib/notificationActions.ts:65` — The `mark_shipped` action (`handleNotificationAction`, which runs before the normal tap handler in app/_layout.tsx) also pushed `/fulfill-order` directly, with no account switch. Same failure as above. Fix: it now uses `openNotificationHref(router, plan.route, data)`. Test: same file, "Mark shipped" case (failed before: yes)
- `artifacts/mobile/lib/notificationSettingsModel.test.ts:14` — Baseline failing "shows each role only its own types". The test is stale: `saved_alerts` was deliberately added as a buyer-only Orders row. It is the `CATEGORY_KEYS` entry in app/notification-settings-page.tsx and the server key in api-server notification-prefs.ts / notificationChannels.ts. Fix: the test now expects `saved_alerts` in the buyer list and checks that sellers do not get it. (The test was the stale part, not the code.) (failed before: yes)
- `artifacts/mobile/lib/previewInbox.ts:191` (accept/delete/theme/disappearing/pinned/nickname) — Each mutation wrote the merged list from `getPreviewConversations()`, which is runtime threads plus seeded ones, back into `cachedConversations`. Failure: after any runtime thread exists (a story reply via getOrCreatePreviewConversationForAuthor), one pin, theme or accept on a seeded thread copies the runtime thread into the cache. The inbox then lists it twice, with duplicate React keys. Separately, a theme or disappearing change on a runtime thread went into the cache while `getPreviewConversation` reads the stale runtime map first, so the change never showed, and deleting a runtime thread did nothing. Fix: a new `updatePreviewConversation` writes to the runtime map or to the seeded cache, wherever the thread lives. Accept and delete handle runtime ids the same way. Test: `artifacts/mobile/lib/__tests__/previewInboxCaches.audit.test.ts` (failed before: yes)
- `artifacts/mobile/lib/previewInbox.ts:320` and `:550` — crosschunk entry VERIFIED. `cachedNotifications` and `cachedSellerConversations` were filled once and never rebuilt when demo mode changed. Demo mode is URL-only, and the buyer inbox is enabled in a fresh preview (`isPreviewInboxEnabled` includes isBuyerDevPreview), so a fresh page cached `[]` and a later `&demo=1` page showed no follower rail or seller threads, and the reverse leaked seeds. Fix: added `cachedNotificationsDemoMode` / `cachedSellerDemoMode`, rebuilt on change, mirroring getPreviewConversations. The assignment lines keep the exact source text that the source-text tests freshInstallPreview.test.ts / demoOnlyFallbacks.test.ts check. Test: same file (failed before: yes)
