How the API client was checked: I loaded `artifacts/api-server/src/routes/index.ts` under tsx and patched Express's `Router.use` to record mount paths. That gave the full live route table: 1,428 method+path pairs, including every nested router. Then I pulled every `/api/...` literal out of lib/api.ts (1,036 call sites) and matched path and method against that table. All 94 entries the script flagged were checked by hand. Every one was either a false positive from the script (a multi-line generic hid the method, or the path is built conditionally, e.g. `invites/:id/${accept?'accept':'decline'}`, `admin/promotions/${boosts|featured}`, `product-import/${shopify-url|instagram}`) or a non-route path (the `signedOutGate` probe paths, `versionApiPath`). **No path or method mismatches remain.** For every call site with an inline object-literal body, I checked each key against the server handler source (dumped via `Function.toString` from the same live router). The 5 flagged keys (`replyText`, `accept`, `commentId`, `note`, `extension`) are all read by the server through shared helpers or schemas, so they are fine. Limitation: bodies passed as a typed variable (`body`) were not checked by script, only spot-checked (close-friends `userIds`/`friendIds`, /api/me/settings keys against `userSettingsPatchSchema`). Every one I spot-checked matched. The scripts are in scratchpad/c14/ (dump.mts, dump2.mts, match.py, body.py).

## Fixes
- `artifacts/mobile/lib/api.ts:765` (doRequest): **204 No Content was parsed with `res.json()`, which throws, so writes that succeeded showed up as failures.** At least 15 server routes reply with a bare 204, and the client calls them through `request()`:
  - DELETE: `/buyer/addresses/:id`, `/shipping-zones/:id`, `/shipping-rates/:id`, `/meta-ads/connection`, `/integrations/klaviyo`
  - POST: `/seller/launch-checklist/{preview-seen,dismiss,store-shared}`, `/seller/milestones/:key/seen`, `/first-run-tips/{:id/seen,skip-all,reset}`, `/buyer/recently-viewed`, `/public/sellers/:id/{visit,store-visits}`
  - Example: deleting a saved address removed it on the server, but the promise rejected with "Unexpected end of JSON input", the screen showed an error, and the API cache was never cleared because the clear runs after parsing.
  - → On 204 the body is `undefined`. The mutation still clears this account's API cache. An undefined GET result is never written to the cache. Test: `artifacts/mobile/lib/api-request.audit.test.ts` (failed before: yes)
- `artifacts/mobile/lib/api.ts:615` (request): **the GET de-dupe key ignored the account scope.** All `createApi` instances share the module-level `inFlightGetRequests` map. After an account switch or sign-in, the new account's GET (e.g. `/api/auth/me`, `/api/buyer/orders`) joined the previous account's in-flight request and got that account's data. → `getCacheScope()` (user id) is now part of the de-dupe key, so same-account callers still share one call. Test: `artifacts/mobile/lib/api-request.audit.test.ts` (failed before: yes)
- `artifacts/mobile/lib/api.ts:5879` (configureApi): **the `api` singleton kept the previous session's bearer token for up to 4s after `configureApi()`.** The token cache is keyed by the wrapper getter `() => _globalGetter()`, which never changes. So after account switch B or sign-out, requests within the 4s TTL still sent A's token. Signed out, that also got past `signedOutGate` (the same hazard `useApi` already guards against). → The singleton now uses a named `globalTokenGetter`, and `configureApi` drops its cache entry. Test: `artifacts/mobile/lib/api-request.audit.test.ts` ("does not send the previous session's cached bearer…", failed before: yes)
- `artifacts/mobile/lib/api.ts` (12 JSDoc blocks): **JSDoc comments that documented the wrong member** (comment-only, no test). Moved each to the member it describes, or removed it where it duplicated a correct doc:

## Cross-chunk defects (not fixed)
- `artifacts/mobile/lib/sellerPaymentStatusCache.test.ts:122` ("does not cache failed requests", a baseline failure): the test is stale, not the code. `doRequest` deliberately retries a failed read once, quietly, after `AUTO_RETRY_DELAY_MS` (lib/requestResilience.ts). Under `vi.useFakeTimers()` that timer never fires, so the test hits its 5s timeout. Also, the quiet retry would consume the second mocked response. → Proposed fix: reject twice (`mockRejectedValueOnce(err)` ×2), `await vi.advanceTimersByTimeAsync(AUTO_RETRY_DELAY_MS)` before asserting the rejection, then expect 3 fetch calls.
- `artifacts/mobile/lib/api.ts:5657-5658` + `artifacts/mobile/app/freelancer-profile.tsx:155` + `artifacts/mobile/lib/sellerBilling.test.ts:31-32`: freelancer-job Stripe Checkout uses `successUrl/cancelUrl 'mobile://checkout/...'` and waits on `openAuthSessionAsync(url, 'mobile://checkout/return')`. The app's scheme is `brandthread` (app.json), and lib/checkoutReturn.test.ts says "never mobile://". On Android and web the redirect never comes back to the app, so a paid hire shows "Checkout not completed". Fixing it in api.ts alone would break the auth-session match in freelancer-profile.tsx, and sellerBilling.test.ts pins the `mobile://` strings (that test is stale; its intent is "don't change buyer checkout", and buyer checkout already uses `currentCheckoutReturnUrls()`). → Proposed fix: in api.ts send `checkoutReturnUrls()`-style `brandthread://checkout-return?session_id={CHECKOUT_SESSION_ID}` / `?cancelled=1`, wait on `NATIVE_CHECKOUT_RETURN_BASE` in freelancer-profile.tsx, and update sellerBilling.test.ts to assert the freelancer URLs use `brandthread://`.
