- `lib/realtime/userEvents.ts:41` — `connect()` had try/finally but no catch: a rejected `serviceSession()` became an unhandled rejection from every fire-and-forget `void connect()` and no reconnect was ever scheduled, so the `/ws/user` hint socket stayed down for the session (this is the baseline unhandled error in `lib/realtime/badgesRealtime.test.ts`, whose mock lacks `serviceSession`) → catch schedules a backoff reconnect. Test: `lib/realtime/userEvents.audit.test.ts` "a failing session lookup is retried…" (failed before: yes). badgesRealtime.test.ts now runs clean (no unhandled error) without touching it.
- `lib/realtime/userEvents.ts` (wiring) — unlike messagesSocket, the user-events socket never reacted to sign-in / sign-out / account switch: it kept the previous user's token-authenticated `/ws/user` connection open (after sign-out too), so the new account got no realtime hints and the old account's hints kept arriving → `onServicesConfigured` now reconnects with the current session (or closes when idle). Registration is wrapped in try/catch because ~60 test files mock `@/lib/serviceConfig` without `onServicesConfigured`. Test: same file, "reconnects with the new session when the active account changes" (failed before: yes).
- `lib/realtime/userEvents.ts` + `lib/realtime/messagesSocket.ts:115` — stale-token race: an account switch while `connect()` is awaiting the token tore down, but the new `connect()` no-oped (`connecting` was true) and the in-flight one then opened the socket with the PREVIOUS account's token → generation counter; a connect whose generation changed during the await discards the token and restarts. Tests: `lib/realtime/userEvents.audit.test.ts` "never opens a socket with a token fetched before the account changed", `lib/realtime/messagesSocket.audit.test.ts` (both failed before: yes).
- `lib/tabDataCache.ts:49` — `hydrateTabData` wrote its AsyncStorage result into memory unconditionally after the await: if the screen's network load called `setCachedTabData` while the disk read was in flight, the older disk snapshot overwrote the fresh data (next `getCachedTabData` painted stale inbox/discover); likewise a read in flight during sign-out's `clearTabDataCacheForUser` repopulated the cleared account's data → per-key write version + clear counter; a read that started before a newer write/clear returns memory instead of landing. Test: `lib/tabDataCache.audit.test.ts` (2 tests, both failed before: yes).
- `lib/saved/savedProductsStore.ts:50` — `load()` only protected ids still `pending`; a toggle that STARTED and FINISHED while a list read was in flight was undone by the older server snapshot (heart flips back to unsaved / re-saved until next refresh) → numbered local changes; ids changed after the read started keep their local value. Test: `lib/saved/__tests__/savedProductsStore.audit.test.ts` (3 tests, failed before: yes).
- `lib/onboarding/useUsernameLiveCheck.ts:23` — the request id was only bumped for values that get sent; clearing the field or making it locally invalid while a check was in flight let that late reply set "Username is already taken." under a name the field no longer held → bump the id on every change. Test: `lib/onboarding/useUsernameLiveCheck.audit.test.tsx` (2 tests, failed before: yes).
