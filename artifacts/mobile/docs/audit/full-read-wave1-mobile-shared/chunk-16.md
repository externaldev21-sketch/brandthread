## Fixes
- `artifacts/mobile/lib/engagementRetryQueue.ts:178-230` — processEngagementRetryQueue iterated the queue and then did `queue = remaining`, overwriting anything enqueueEngagementRetry added while a replay was awaited. Scenario: offline, a pass is waiting on a like replay; the buyer likes another post → that like is dropped from memory and storage (lost forever). A re-tap on the same target during the pass was also undone: the pass's retry copy (old intent) came back and the new one was lost. → snapshot the queue for the pass, then merge: actions added during the pass are kept and win over the pass's copy of the same (kind, target). Test: `artifacts/mobile/lib/engagementRetryQueue.audit.test.ts` (failed before: yes, 2 cases)
- `artifacts/mobile/lib/feedPostsCache.ts:103-120` — purgeAuthorFromFeedPostsCache re-derived the key via scopedTab(tab) AFTER awaiting storage; an account switch during that await wrote account A's filtered For You/Following page into account B's memory and disk cache (B would paint A's feed on cold start). → capture the account-scoped key before the await (shared readFeedPostsCache(scoped) helper; hydrateFeedPostsCache behaviour unchanged). Test: `artifacts/mobile/lib/__tests__/feedPostsCache.audit.test.ts` (failed before: yes)
- `artifacts/mobile/lib/finishedVideos.ts:76-83` — markVideoFinished built the new map from the value its load promise resolved with; two marks made while the first load was pending both resolved with the same initial map, so the second overwrote the first (memory + AsyncStorage) and a finished video was not ordered after unseen ones. → build on the current `memory ?? loaded`. Test: `artifacts/mobile/lib/finishedVideos.audit.test.ts` (failed before: yes)
- `artifacts/mobile/lib/installId.ts:26-39` — getInstallId had no in-flight guard: two concurrent first calls (lib/api.ts postWithInstallId) each generated a different random UUID; requests carried different x-bt-install-id values and the stored one was whichever wrote last, defeating the server's one-per-device rule. → share one in-flight promise. Test: `artifacts/mobile/lib/installId.audit.test.ts` (failed before: yes)
- `artifacts/mobile/lib/imageUri.ts:118-120` — native makeDurableUri took `pickerUri.split('.').pop()` as the extension, so the documented `ext` hint was never used and a URI without an extension in its last segment (Android content://…/42, or a dotted package folder like com.app.x/cache/abc) produced a "extension" containing slashes → File(Paths.document, 'img_….content://media/…') → copy fails / wrong name. → use the last path segment's extension when it looks like one (1–5 alnum), else the caller's hint. Test: `artifacts/mobile/lib/imageUri.audit.test.ts` (failed before: yes)
- `artifacts/mobile/lib/mediaCrop.ts:133-149` — transformFromNormalizedRect computed scale as sourceW / cropWidth, but resolvePixelCropRect's scale is relative to the scale-1 box (largest box of the target ratio that fits). For any source wider than the target ratio (landscape photo → 3:4, any 16:9 video → 9:16) "Edit crop" reopened zoomed in and framed differently (an untouched centered crop on 1920x1080 at 9:16 reopened at scale ~3.16). → scale = baseBox(ratio from rect).width / cropWidth. Existing tests/mediaCrop.test.ts only covered a source exactly at 3:4. Test: `artifacts/mobile/lib/mediaCrop.audit.test.ts` (failed before: yes)
- `artifacts/mobile/lib/growthLinks.test.ts:9-22` — baseline-failing test ("lets a guest through every share-link entry point", "opens both the live directory and shared-live viewer to guests") was stale vs a deliberate product change: commit a7c64de9 "Account wall: remove guest browsing, require an account for every app screen" made isGuestBrowseRoute always false, and lib/guestRoutes.test.ts asserts `['live']` etc. are NOT guest routes. Updated the two cases to assert the account wall (same entry points, now `false`); the share-link parsing cases are unchanged. Test: the file itself (failed before: yes)
